Several kinds of authorization can now work together on one server, and standalone servers get organizations, personal namespaces and GitHub login. Without new configuration, a server behaves as in v0.1.5.

## Install

```sh
# The client, scn
curl -fsSL https://raw.githubusercontent.com/OpenCSGs/scion/main/install.sh | sh
# and the server, as a service on 127.0.0.1:7080 (systemd on Linux, launchd on macOS)
curl -fsSL https://raw.githubusercontent.com/OpenCSGs/scion/main/install.sh | sh -s -- --server
```

**Release packages.** As in v0.1.5, the server `scion` comes in `scion-server-v0.1.6-<target>.tar.gz` and the client in `scn-v0.1.6-<target>.tar.gz`, with `SHA256SUMS` and `install.sh`. The targets are:
- `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` (glibc 2.35 or newer);
- `aarch64-apple-darwin` and `x86_64-apple-darwin`.

**Docker image.** The server image is `opencsg-registry.cn-beijing.cr.aliyuncs.com/opencsghq/scion:0.1.6`, for `linux/amd64` and `linux/arm64`.

**Upgrading a server.** The server adds the `orgs` and `org_members` tables (migration 0019) when it starts. Back up the metadata database first.

## Changes

All of this is configured in `auth.toml` and described in [authentication](https://github.com/OpenCSGs/scion/blob/main/docs/guide/auth.md); the design is in [authorization](https://github.com/OpenCSGs/scion/blob/main/docs/design/authorization.md).

- **An authorization chain.** Deciders are asked in order: `policy`, `grants`, `orgs`, `personal` and named webhooks. Each one allows, denies or abstains, and the first that allows or denies settles the request. Configure it with `[authorization] chain = [...]`.
- **Several webhooks.** There can be several, each limited to the repositories it covers (`repos`). With `decides = "allow-deny"`, a webhook's "no" denies, so one server can, for example, send `models/*` to starhub and everything else to OPA.
- **Deny rules and groups in the policy.** `effect = "deny"` rules win over allow rules. `[groups]` defines groups from users and other groups.
- **Organizations.**
  - An organization owns the repositories named `ORG/…`.
  - Members are owners (admin), maintainers (land), developers (write) or reporters (read).
  - An organization is `private` or `internal`.
  - Any signed-in user can create one with `scn org create` and becomes its owner. Owners manage members with `scn org member add / rm / ls`; operators use `scion admin org`.
  - Membership changes take effect at once on the server that made them, and within 30 seconds on other nodes. There is no need to issue new tokens.
- **Personal namespaces.** With `personal` in the chain, every signed-in user owns `user/LOGIN/…`.
- **GitHub login.**
  - Add `[github] client_id = "…"` for an OAuth app with the device flow enabled. `scn login SERVER` then shows a code to enter at github.com/login/device.
  - The subject is the GitHub login, and the server issues its own tokens.
  - With `orgs` and `token_env`, members of GitHub organizations and teams get the groups `github:ORG` and `github:ORG/TEAM`.
  - The server must reach github.com: set `HTTPS_PROXY` if it needs a proxy.
