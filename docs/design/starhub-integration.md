# Connecting Scion to starhub-server (alongside Gitaly)

English | [简体中文](starhub-integration.zh-CN.md)

> Version: Draft v0.1 · 2026-10-16
> Studied: the local `~/git/starhub-server` (module `opencsg.com/csghub-server`; Go, gin + bun + Temporal)
> Prerequisites: [`rust-server-architecture.md`](./rust-server-architecture.md), [`rust-client-architecture.md`](./rust-client-architecture.md)

Goal: Scion deploys both as a **standalone product** and as starhub's **second git storage backend**, running **per repository alongside** the existing Gitaly, with repositories movable between the two backends and back when needed.

---

## 1. starhub-server today (the git-related parts)

### 1.1 Layers and the git abstraction
- Layering: `handler → component → builder` (see `AGENTS.md`).
- **The only git abstraction:** the `GitServer` interface in `builder/git/gitserver/interface.go`, about 45 methods covering repositories, branches, commits, file trees, reading and writing files, diffs, archives, LFS pointers, mirrors, smart HTTP, forks, sizes and so on.
- **The only implementation:** `builder/git/gitserver/gitaly/`, about 4,000 lines over the Gitaly v16 gRPC client.
- **The factory is hard-wired:** `NewGitServer()` in `builder/git/gitserver.go` returns `gitaly.NewClient(config)`.
  - `STARHUB_SERVER_GITSERVER_TYPE: gitaly` in docker-compose **is not used in the code**.
  - Gitaly is configured with **a single storage and a single address** (`config.GitalyServer.Address/Storage`).
- **Used widely:** about 60 non-test files depend on `gitserver.GitServer`, and `git.NewGitServer` has 53 call sites across component, callback, checker, dataviewer, moderation, mirror, user and workflow.

### 1.2 git protocol entry points
| Entry | Path | Implementation |
|---|---|---|
| Smart HTTP | `/{type}s/:ns/:name.git/info/refs`, `git-upload-pack`, `git-receive-pack` | `api/handler/git_http.go` → `GitServer.InfoRefs/UploadPack/ReceivePack` → Gitaly's SmartHTTPService |
| SSH | gitlab-shell v16 → `/api/v4/internal/allowed` for authorization | **The response carries Gitaly's address and token** (`component/internal.go:139`), and gitlab-shell then talks to Gitaly directly |
| Push hooks | Gitaly hooks → `/api/v4/internal/pre_receive`, `/post_receive` | `post_receive` computes the added/removed/modified files with `GetDiffBetweenTwoCommits`, builds a `types.GiteaCallbackPushReq` and starts the Temporal `HandlePushWorkflow` |

### 1.3 The pipeline after a push (`component/callback/git_callback.go`)
Repository metadata and tag updates, parsing model and dataset information, watching Space changes, repository relations, sync versions, repository size statistics, sensitive content checks and so on. **All of it depends only on `GiteaCallbackPushReq` and on reading files back through `GitServer`**, whatever the backend.

### 1.4 Large files
- starhub has its own LFS service: batch, upload and download, locks, multipart; metadata in the `lfs_meta_objects` table (sha256 oids), objects in S3/MinIO.
- **Xnet:** another large-file backend (Xet-style). It works by a switch on the repository table, `repositories.xnet_enabled`, with the `xnet_migration_task` table and the Temporal workflow `batch_migrate_to_xnet` for migration; repositories with Xnet **refuse git operations** (`ErrUsingGitInXnetRepository`, pointing at the SDK/CLI).
- It also serves a **HuggingFace-compatible API** (the `hfGroup` routes), which relies on LFS's sha256 and HF's file tree semantics.

> **Conclusion:** Xnet is a ready-made template of "switch the backend per repository + a migration task + a workflow", and Scion should **copy this pattern exactly**.

## 2. The overall plan

![Scion connected to starhub-server](./images/arch-03-starhub-integration.png)

```
                       starhub-server (Go)
   handler ──▶ component ──▶ builder/git
                                │
                     RoutingGitServer  (new; implements gitserver.GitServer)
                     dispatches on repositories.storage_backend
                     ┌──────────┴───────────┐
               gitaly.Client           scion.Client (new adapter)
                     │                       │ gRPC (Go stubs generated by buf)
                  Gitaly                scion server / cache (Rust)
                     ▲                       ▲
 git CLI ─ Smart HTTP┤                       ├─ scion-git-gateway (Rust, stage 3)
 git CLI ─ SSH ──────┘ gitlab-shell ─────────┘   implements a subset of Gitaly's SmartHTTP/SSH services
                                              (/allowed returns a different address per repository)
 scn / agents / CI ────────────────────────────▶ scion (native protocol, the default client)

 Scion events ──NATS (already used by starhub)──▶ starhub consumer ──▶ turned into GiteaCallbackPushReq
                                                  ──▶ the same Temporal HandlePushWorkflow
 Scion pre-land webhook ──▶ starhub /internal/scion/pre_land (reusing checker: file size/LFS/sensitive)
 JWTs issued by starhub ──JWKS──▶ verified by Scion (repository-level permission claims)
```

**Principles:**
1. **The Scion server does not depend on starhub:** every connection point is one of Scion's general extension mechanisms (external JWKS, the pre-land webhook, NATS events, the repository management API). A standalone deployment just leaves them off.
2. **starhub's changes stay in the builder layer**, plus a minimum of routes and configuration; business logic in component and above changes **not at all**, and neither does the post-push pipeline.

## 3. Changes on starhub's side

### 3.1 Data model (generated with the repository's migration CLI, not written by hand)
```
repositories
  + storage_backend   text not null default 'gitaly'   -- 'gitaly' | 'scion'
  + current_backend_migration_task_id bigint null

backend_migration_tasks          (modeled on xnet_migration_task)
  id, repository_id, from_backend, to_backend, status, phase, last_message, times
```

### 3.2 `RoutingGitServer`
- Implements `gitserver.GitServer` and holds both implementations, `gitaly.Client` and `scion.Client`. Each method looks up the repository's backend from the request's `(RepoType, Namespace, Name)` or `relativePath` (cached locally with `golang-lru`, invalidated through Redis pub/sub) and forwards to that implementation.
- `NewGitServer()` returns a `RoutingGitServer` instead. **The 53 call sites need no changes.**
- `CreateRepo`'s default backend comes from the setting `STARHUB_SERVER_GITSERVER_DEFAULT_BACKEND`, and can be rolled out gradually by repository type or organization.

### 3.3 `builder/git/gitserver/scion` (the Go adapter)
> Note: Go stubs generated by buf from Scion's protos, plus the method mapping, an estimated 1,500 to 2,500 lines; it can be written whenever needed and is off the critical path.

**Method mapping** (★ marks what Scion needs to add; see §5):

| GitServer method | Scion counterpart |
|---|---|
| CreateRepo / DeleteRepo / GetRepo / UpdateRepo / RepositoryExists | ★ `RepoAdminService.Create/Delete/Get/Update` |
| CreateFork / CopyRepository | ★ `RepoAdminService.Fork`: objects are deduplicated globally, so a fork copies only refs, O(1) |
| CreateBranch / DeleteRepoBranch / GetRepoBranches / GetRepoBranchByName / SetDefaultBranch / UpdateRef | `RefService` (★ plus a default-branch property) |
| GetRepoCommits / GetRepoLastCommit / GetSingleCommit | `QueryService.Log` / `ResolveRevision` |
| GetCommitDiff / GetDiffBetweenTwoCommits | `QueryService.Diff` (GetDiffBetweenTwoCommits's added/removed/modified come straight from the changeset delta) |
| GetRepoFileTree / GetTree / GetRepoAllFiles / GetRepoFiles / GetFilesByRevisionAndPaths | `ListDir` / `GetTrees` (recursive) |
| GetLogsTree (the last commit of each entry of a directory) | ★ the derived data `LastCommitPerEntry` |
| GetRepoFileRaw / GetRepoFileReader / GetRepoFileContents | `QueryService.ReadFile` (streamed) |
| CreateRepoFile / UpdateRepoFile / DeleteRepoFile / CommitFiles | `CreateChangeset` (inline content) + `Land` |
| GetArchive | ★ `QueryService.Archive` (streamed tar.gz/zip) |
| GetRepoLfsPointers / GetRepoAllLfsPointers | ★ the derived data `LfsPointerIndex` |
| GetRepoSize / GetLastCommitSize / GetRepoLfsSize | ★ the derived data `TreeStats` (size, file count) |
| CreateMirrorRepo / MirrorSync | ★ `ImportService`: the server imports incrementally from a remote git, an online scion-import |
| InfoRefs / UploadPack / ReceivePack | Stages 1–2: return `ErrUsingGitInScionRepository` (copying Xnet); stage 3: hand over to the git gateway |
| BuildRelativePath | Compute the Scion repository name locally, independent of Gitaly's path rules |

**Commit id compatibility:** many places in starhub, the front end and the HF API expect commit ids to be 40-digit hex SHAs. The adapter always returns the **git-compatible SHA-1** from Scion's derived data `GitSha`, and maps it back to Scion's changeset id internally. URLs, cache keys and HF's `revision` parameter keep their formats, so switching the backend is invisible to users.

### 3.4 Push events
A new NATS consumer, `scion-ref-events`, subscribes to `scion.<repo>.ref.updated`, turns each event into a `GiteaCallbackPushReq` (ref, commits, each commit's added/removed/modified, head_commit) and starts `HandlePushWorkflow` with **the same workflow id rules**. Everything downstream is reused, and Temporal's workflow ids deduplicate.

### 3.5 Checks before a push
A new internal endpoint, `POST /api/v1/internal/scion/pre_land`, reuses `component/checker` (file sizes, LFS object existence, skill file rules) and the logic of `pre_receive`. Scion calls it synchronously before a land.

### 3.6 Authentication and authorization
> Revised 2026-10-17 after starhub-server's actual implementation (the earlier assumption that starhub offers JWKS and a `repos` claim was wrong). Scion uses only standard protocols, with no starhub-specific code; the configuration is in [`docs/guide/auth.md`](../guide/auth.md#connecting-starhub-server).

- **starhub's JWTs:** signed with an HS256 shared secret (`STARHUB_JWT_SIGNING_KEY`), `iss = "OpenCSG"`, the user name in `current_user`. Scion configures starhub as an HS256 issuer (`hs256_secret_env`, `subject_claim = "current_user"`) and verifies them directly.
- **starhub's access tokens** (opaque): Scion calls starhub's introspection endpoint as in RFC 7662. starhub adds `POST /api/v1/internal/scion/introspect`, which calls `VerifyByAccessToken`.
- **Permissions:** stay in starhub (rebac, organization inheritance, public and private repositories). Scion calls starhub's authorization endpoint in an OPA-compatible format. starhub adds `POST /api/v1/internal/scion/authz`, which maps the repository name back to the starhub repository and calls `CheckUserRepoPermission`. Scion caches the results (allows for 30 seconds, denials for 5).
- When `scn` reaches a Scion hosted by starhub, `scn login` goes through starhub's Casdoor OIDC (device flow), or `scn login --token <access token>` is used.

## 4. Migration: Gitaly ↔ Scion (copying the Xnet pattern, a Temporal workflow)

```
MigrateRepoToScion(repo):
  1. Precheck   : repository size, LFS state, Xnet on or not, any mirror in progress
  2. Bulk import: scion ImportService reads from Gitaly (internal git URL) → changesets + GitSha mapping
  3. Freeze     : make the repository read-only (pre_receive refuses writes), record each ref's sha
  4. Catch-up   : import incrementally the commits between Bulk and Freeze
  5. Verify     : for each ref, the git tree sha must equal the GitSha tree Scion derives
  6. Flip       : repositories.storage_backend = 'scion', invalidate the routing cache, unfreeze
  7. Retain     : keep Gitaly's copy N days for a read-only rollback, then delete it
Rollback: the reverse flow (Scion → git fast-export → Gitaly), or within the retention period switch back and catch up
```
- Bulk migrations reuse the concurrency control and admin entry points of `batch_migrate_to_xnet` (`api/router/admin*.go`).
- **The freeze covers only Catch-up to Flip**, usually seconds.

## 5. General capabilities the Scion server needs

These go into §16 of the server architecture document as well. They are all **general mechanisms**, useful for standalone deployments too:

| Capability | What |
|---|---|
| `RepoAdminService` | Create/Delete/Get/Update/Fork/List; repository properties (default branch, visibility flag, quota). Multi-tenant with many small repositories from day one (starhub's models, datasets and Spaces are separate repositories) |
| External identities (done in M5) | Trusted issuers: JWKS (standard OIDC) or an HS256 shared secret (starhub today), with configurable claim mapping; RFC 7662 introspection for external opaque tokens |
| External authorization callback (done in M5) | OPA-compatible: `{"input": {subject, groups, repo, action, ref, path}}` → `{"result": bool}`, cached with a TTL; starhub plugs its rebac in through it |
| Pre-land webhook | Called synchronously, with a configurable timeout and failure handling (fail-open or fail-closed); sends the delta and file metadata to an external system to check |
| Events | `scion.<repo>.ref.updated` (with each commit's path-level delta) on NATS, optionally as a webhook too |
| Derived data | `GitSha` (git-compatible commit/tree/blob SHA-1), `LastCommitPerEntry`, `LfsPointerIndex`, `TreeStats`, blobs' `Sha256` (for LFS/HF) |
| `QueryService.Archive` | Streams tar.gz/zip, with path filtering |
| `ImportService` | Incremental imports from a git remote or a local path, for mirrors and migration |
| `scion git-gateway` (a new role) | A Rust implementation of **a subset of Gitaly's SmartHTTPService / SSHService** (info-refs, upload-pack, receive-pack, sidechannel included). git objects are generated on demand from the `GitSha` derived data; a push parses the received packfile into changesets and lands them |

**Metadata database:** with starhub, the **Standard tier (PostgreSQL)**: a **separate database** (`scion`, say) in starhub's PG cluster, sharing Patroni and the backups without mixing with starhub's tables; moved to YugabyteDB on its own once it grows.

**Sharing object storage (MinIO):**
- Scion uses starhub's existing MinIO directly (the `minio` service in compose, and MinIO or cloud OSS in production), by default in **a separate bucket, `scion-objects`**, or isolated in the same bucket under `prefix = "scion/"`. Credentials are injected from starhub's deployment configuration.
- MinIO compatibility settings (path-style addressing, checksums `when_required`, a self-test at start) are in §4.6 of the server document.
- Large files can be downloaded straight from MinIO through presigned URLs, as starhub's LFS downloads already return object storage addresses, which suits the HF SDK.

**Large files:**
- In stage 1, Scion repositories **still hold LFS pointer files**, and the data stays in starhub's LFS and Xnet storage. The LFS endpoints, the `lfs_meta_objects` table and Xnet **need no changes at all**.
- Later, large files can become Scion-native chunked blobs, still compatible with the LFS and HF protocols through the `Sha256` derived data.
- **Migrating without copying data:** stage S4 adds an "external blob" object type (`ExternalBlob{bucket, key, sha256, size}`) that refers to starhub's existing LFS objects in MinIO, converted to Scion-native chunked storage in the background as needed, so migrating terabyte-sized model repositories needs no second full copy.

## 6. Stages

| Stage | What | starhub side | Scion side | What users see |
|---|---|---|---|---|
| **S0 Preparation** | The backend routing layer ships; every repository still uses Gitaly | The `storage_backend` field, `RoutingGitServer`, settings | — | Nothing changes (a safe release) |
| **S1 Pilot with new repositories** | New repositories of chosen organizations or types are created on Scion | The scion adapter (read/write APIs, branches, commits, files), the NATS consumer, the pre_land endpoint, JWT/JWKS | RepoAdmin, JWKS, the pre-land webhook, events, GitSha/LastCommitPerEntry/TreeStats, Archive | The web pages, the HF SDK and `scn` work; the git CLI says "use scn" (as with Xnet) |
| **S2 Migration** | Existing repositories migrate both ways | The migration workflow, the admin console | ImportService | Bulk migration, with rollback |
| **S3 git compatibility** | git clone/push on Scion repositories | `/allowed` and smart HTTP return the gateway's address per repository | git-gateway | The git CLI works transparently on Scion repositories |
| **S4 Native large files** | LFS data moves into Scion's chunked blobs | The LFS handler routes to Scion | The Sha256 derived data, chunked storage | Large model files fetched on demand, deduplicated globally |

## 7. Risks and open questions

1. **How deep Gitaly protocol compatibility goes:** sidechannel, differences between gitlab-shell versions and so on, which need protocol-level tests against Gitaly's protos first. The git gateway is the largest piece of work, hence stage S3.
2. **Code that assumes 40-digit hex commit ids:** needs a full sweep of starhub (front-end routes, cache keys, HF revisions, `sync_version`), with the `GitSha` mapping as the fallback.
3. **The number of small repositories:** starhub may have hundreds of thousands. Scion's metadata tables are keyed by `repo_id`, but per-repository fixed costs (eager derivation workers' shards, land leaders) must be loaded lazily, not kept for every repository.
4. **The SaaS / EE / CE editions:** `RoutingGitServer` belongs in shared code; the Scion backend can be on in EE/SaaS only at first (copying Xnet's `_ce/_ee` file split).
5. **The permission model:** starhub has rebac, organization inheritance, `org_inherit_blocked` and other rules. A live authorization callback with a short TTL cache comes first, rather than putting complex permission computation into token claims.

## 8. With CSGLite (later)

![Scion × CSGLite](./images/arch-04-csglite-integration.png)

CSGLite (`~/git/csglite`) is a single-binary local inference tool in Go: embedded SQLite (`modernc.org/sqlite`), llama.cpp/MLX for inference, LAN clusters found through mDNS. Today it downloads models through starhub's HF-compatible endpoint `/api/v1/{type}/{ns}/{name}/resolve/{path}` (`internal/csghub/download.go`).

These four approaches stack, from the lightest to the deepest:

| # | Approach | CSGLite changes | Value |
|---|---|---|---|
| ① | **Indirect:** CSGLite keeps calling `/resolve`; starhub routes the request to Scion, and large files 302 to presigned MinIO URLs | None | CSGLite works as soon as repositories move to Scion |
| ② | **Native fetching:** a built-in Scion fetcher (Go, generated from the protos) fetching chunks and checking BLAKE3 | A new fetcher | Chunks shared by different models download once (quantized and fine-tuned versions share a lot); resuming is built into the protocol |
| ③ | **LAN peer caching:** every node is an L1, and neighbors fetch from each other through the same `ObjectService` before going to L2 | A new read cache on the existing mDNS cluster | Replaces copying models between nodes; sharing by object hash checks itself |
| ④ | **A local Lite repository:** an embedded `scion server --lite` (SQLite + the local file system, CSGLite's own stack) | Optional embedding | Version control for locally fine-tuned models, datasets and agent workspaces, landed to CSGHub later |
